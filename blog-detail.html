Core Web Vitals: which fixes actually move the number

  • Updated 20 July 2026
  • Technical Lead Author

Every few months a client forwards a Lighthouse report with a red score and asks what it will cost to fix. The honest answer is usually that the report is listing thirty issues of which two matter, and identifying which two is most of the work.

This is the order of operations we actually use. It assumes you have no dedicated performance engineer and a finite number of sprints, which describes most marketing teams.

What is actually being measured

Three metrics carry weight. It is worth being precise about them, because a lot of wasted effort comes from optimising the wrong one.

  • Largest Contentful Paint (LCP) — how long until the biggest element in the initial viewport finishes rendering. Usually a hero image, sometimes a heading. Target is under 2.5 seconds.
  • Interaction to Next Paint (INP) — how long the page takes to visually respond after a user interacts. This replaced First Input Delay and is considerably harder to pass. Target is under 200 milliseconds.
  • Cumulative Layout Shift (CLS) — how much content moves around during load. Target is under 0.1.

Note that none of these measure "how fast the page feels" in the abstract. They measure three specific, separately caused things, and the fixes for each barely overlap.

Lab data is not field data Lighthouse runs a simulated device on a simulated network. Search Console reports what real Chrome users experienced. When they disagree, the field data is the one that counts — use Lighthouse to find causes, not to judge whether you have a problem.

LCP: the four causes, in order of frequency

Most teams assume a failing LCP means the hero image is too large. In our audits that is the cause roughly a quarter of the time. The other three are more common and less obvious.

Resource load delay

The browser does not discover the LCP image until late, because it is set in CSS as a background, injected by JavaScript, or lazy-loaded by a plugin that does not distinguish above-the-fold content from the rest.

The fix is unglamorous and usually cheap: put the image in an <img> tag, give it fetchpriority="high", and make certain it does not carry loading="lazy". A surprising proportion of LCP failures are a single misapplied lazy-load attribute.

Render-blocking resources

Stylesheets and synchronous scripts in the document head must download and execute before anything paints. Every third-party tag added in that position delays the first paint for every visitor.

Audit what is actually in your head. Consent managers, chat widgets, heat-map tools and tag managers frequently sit there for no reason other than that the installation instructions said to put them there.

Slow server response

If Time to First Byte is over 800 milliseconds, no amount of front-end optimisation will rescue LCP. Common causes are unindexed database queries, an uncached CMS, or hosting in the wrong region for your audience.

Image size and format

The cause everyone assumes. It is real, and it is the easiest to fix: serve WebP or AVIF, size the asset to its rendered dimensions, and provide a srcset so mobile does not download a desktop-sized file. If this is your only problem, you have a good afternoon's work rather than a project.

The order matters more than the list. Compressing images on a site with an 800ms server response is optimising the last 20% of a problem while ignoring the first 80%.

INP: the metric most sites now fail

INP is stricter than the metric it replaced, and it punishes a pattern that is extremely common: a page that loads acceptably and then blocks the main thread whenever anyone touches it.

The usual culprits, in order:

  1. Third-party scripts executing long tasks on the main thread. Chat widgets, analytics, A/B testing tools and personalisation engines are the frequent offenders.
  2. Large JavaScript bundles that must be parsed before any interaction can be handled.
  3. Expensive event handlers doing layout-triggering work synchronously on scroll or input.
  4. Excessive DOM size. Style recalculation cost scales with node count, and page builders routinely produce 3,000-node pages.

The most effective single action is usually removal rather than optimisation. Audit your third-party tags and delete the ones nobody has looked at in six months. We have never run this audit without finding at least two.

CLS: mostly a solved problem

CLS is the easiest of the three to fix because the causes are few and mechanical:

Common causes of layout shift and their fixes
Cause Fix
Images without dimensions Always set width and height, or use aspect-ratio
Webfonts causing reflow font-display: swap plus a metrics-matched fallback
Injected banners and notices Reserve the space, or overlay rather than push content
Embeds and iframes Wrap in a container with a fixed aspect ratio
Late-loading ad slots Reserve the largest expected size for the slot

If CLS is failing, the cause is almost always the first row of that table.

The order we work in

Given a failing site and a limited budget, this is the sequence. It is deliberately front-loaded with cheap diagnostic work.

  1. Get field data. Search Console and the CrUX report. Establish whether there is a real problem before spending anything.
  2. Identify the LCP element per template. It differs between homepage, product and article pages.
  3. Check for lazy-loading on the LCP image. Free to fix, and it is the cause more often than anyone expects.
  4. Measure TTFB. If it is over 800ms, stop and fix the back end first.
  5. Audit third-party tags. Delete what is unused. This helps LCP and INP simultaneously.
  6. Fix image dimensions and formats. Mechanical, reliable, helps LCP and CLS.
  7. Then, and only then, consider code splitting, critical CSS and the more expensive interventions.

When to stop

Passing all three thresholds is worth doing. Chasing a perfect Lighthouse score is not. Beyond the thresholds the returns fall off sharply, and the engineering effort is almost always better spent on conversion work — where the measurable business effect is larger.

We set a performance budget at the start of a build precisely so this conversation happens once, in advance, rather than as an open-ended pursuit after launch.

They are a ranking signal, but a weak one relative to relevance and authority. A fast page about the wrong topic will not outrank a slower page that answers the query.

The stronger business case for performance is conversion: speed affects whether visitors stay long enough to convert, and that effect is far larger than the ranking effect.

Lighthouse is a lab test on a simulated device and network. Search Console reports field data from real Chrome users on their real devices and connections.

Field data is what counts for the ranking signal. If they disagree, trust the field data and treat Lighthouse as a diagnostic tool.

Field data uses a 28-day rolling window, so a fix deployed today takes roughly four weeks to be fully reflected. Partial movement appears sooner.

This lag is the most common reason teams conclude a fix did not work when it simply has not surfaced yet.
